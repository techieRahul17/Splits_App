## Ways to contribute

You do not need to write Dart to help:

- Report a bug with clear reproduction steps
- Improve the documentation where it is unclear or out of date
- Suggest a feature, along with the problem it solves
- Test on a device or screen size we have not covered and report what breaks
- Review an open pull request

If you plan to work on something substantial, open an issue first so we can agree on the
approach before you spend time on it.

## Local setup

### Prerequisites

- Flutter SDK 3.41 or newer, with Dart 3.11
- Android Studio or Xcode for device tooling
- An emulator, simulator, or physical device

### Getting running

```bash
git clone https://github.com/<your-username>/splits-app.git
cd splits-app
flutter pub get
flutter run
```

Verify your toolchain with `flutter doctor` if anything fails to build.

### Regenerating model adapters

`lib/models/models.g.dart` is generated by `build_runner`. If you change an annotated model,
regenerate it and commit the result:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Never hand-edit `models.g.dart`.

### A note on Hive type IDs

Each model carries a `@HiveType(typeId:)`. These IDs are written into stored data, so
**changing or reusing an existing ID will corrupt every existing user's database**. When
adding a model, take the next unused ID. When adding a field, give it a new `@HiveField`
index and never reuse a retired one.

## Project structure

```
lib/
  main.dart                     Entry point, Hive setup, theme wiring
  models/                       Data models and generated adapters
  providers/                    Riverpod state, all reads and writes
  screens/                      One file per screen
  theme/app_theme.dart          Palette, tones, spacing and radius tokens
  utils/router.dart             Route tree
  utils/split_calculator.dart   Pure money logic
  widgets/common_widgets.dart   Shared component library
test/                           Unit tests
```

Two rules keep this structure honest:

1. **Money logic goes in `split_calculator.dart`**, as pure functions with no Flutter or
   Hive imports. This is what makes it testable.
2. **Writes go through `GroupsNotifier`.** Screens never touch a Hive box directly.

## Coding conventions

Before pushing, both of these must be clean:

```bash
dart format .
flutter analyze
```

Beyond the analyzer:

- **Reuse components.** Check `widgets/common_widgets.dart` before building a new button,
  card, chip, or sheet. If you need a variant, extend the existing widget rather than
  writing a parallel one.
- **Use `SheetScaffold` for every bottom sheet**, so padding, the grab handle, keyboard
  avoidance, and scrolling behave identically everywhere.
- **Prefer `const` constructors** wherever the analyzer suggests them.
- **Comment the why, not the what.** Explain a non-obvious constraint or a subtle
  workaround. Do not narrate code that already reads clearly.
- **Guard against overflow.** Any row holding user-supplied text, such as a name or a
  group title, needs `Flexible` or `Expanded` plus `TextOverflow.ellipsis`. Long names are
  the most common source of layout breakage in this app.

## Working with the theme

**Never hardcode a colour in a screen.** Every colour resolves from the palette:

```dart
final p = AppPalette.of(context);

Text('Total', style: TextStyle(color: p.textPrimary));
```

The palette separates fills from text for a reason. Gold is bright enough to work as a
background but is unreadable as text on white, so light mode substitutes a deeper bronze:

| Use case                            | Correct value                            |
| ----------------------------------- | ---------------------------------------- |
| Solid accent fill, such as a button | `SplitsColors.primary`                   |
| Text or icon sitting on that fill   | `SplitsColors.onGold`                    |
| Accent text on a page or card       | `p.accentText`                           |
| Success, error, or info text        | `p.positiveText`, `p.negativeText`, `p.infoText` |
| Tint behind a coloured chip         | `tone.base().withOpacity(p.tint)`        |

For semantic states, prefer a `Tone` over a raw colour, since `Tone` resolves per theme:

```dart
StatusPill(label: 'Active', tone: Tone.info);
```

Spacing and corner radii come from `SplitsSpacing` and `SplitsRadius`.

**Check both themes before opening a pull request.** Toggle dark and light from the icon
on the home screen. A change that looks correct in dark mode very often fails in light
mode, and that is the single most common review comment on this project.

## Working with money

Money bugs are the ones users actually notice, so this area has stricter rules.

- **Amounts are `double`, rounded to two decimals at every boundary.** Use
  `double.parse(value.toStringAsFixed(2))` when returning a computed total.
- **Shares must sum exactly to the item price.** `computeShares` floors each share and
  gives the remainder to the last unlocked member. If you touch this function, the sum
  invariant must still hold for awkward cases such as 100 split three ways.
- **Never sum across currencies.** Groups each carry their own currency. Bucket totals per
  currency instead, as the home screen does.
- **Format for display with `formatMoney`**, which adds thousands separators. Do not
  concatenate a symbol with `toStringAsFixed` in new UI code.
- **Any change to `split_calculator.dart` needs tests.**

## Testing

```bash
flutter test
```

The suite covers the split engine: even division, rounding remainders, locked shares,
per-member totals, outstanding balances, currency formatting, and UPI link construction.

If you fix a calculation bug, add a test that fails without your fix. If you add a
calculation, cover the ordinary case and at least one awkward one, such as a value that
does not divide evenly or a group where everything is locked.

## Commits and branches

Branch from `main` using a descriptive prefix:

```
feature/multi-payer-splits
fix/summary-overflow-long-names
docs/contributing-guide
refactor/sheet-scaffold
```

Write commit subjects in the imperative mood, under about 72 characters:

```
Add per-currency bucketing to the outstanding total
Fix payee chip overflow with long member names
```

Explain the reasoning in the commit body when the change is not self-evident. Keep
unrelated changes in separate commits.

## Pull requests

Before opening one:

- [ ] `dart format .` produces no changes
- [ ] `flutter analyze` reports no new issues
- [ ] `flutter test` passes
- [ ] You have checked the change in **both dark and light mode**
- [ ] You have checked it on a small screen, where text is most likely to overflow
- [ ] Any new user-facing string reads naturally

In the description, include:

- What the change does and the problem it solves
- A screenshot or screen recording for any visual change, ideally both themes
- The issue it closes, if there is one
- Anything you are unsure about, so reviewers know where to focus

Small, focused pull requests get reviewed much faster than large ones. If a change is
growing, consider splitting it.

---

## Reporting bugs

Open an issue with:

- What you expected and what actually happened
- Numbered steps to reproduce
- Device, OS version, and app version
- Whether it happens in dark mode, light mode, or both
- A screenshot or recording where relevant

For anything with security or privacy implications, follow [`SECURITY.md`](SECURITY.md)
instead of opening a public issue.

---

## Suggesting features

Describe the problem before the solution. The most useful feature requests explain the
situation where the current app falls short, who it affects, and how often it comes up. A
proposed design is welcome, but the problem is what we discuss first.
